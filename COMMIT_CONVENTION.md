# Соглашение по коммитам

## Сообщение коммита

Сообщение коммита делится на две части: обязательный заголовок и опциональное
описание.

```
Это обязательный заголовок

Это опциональное описание.

Это ещё один абзац описания.
```

Заголовок может состоять лишь из одной строки. Заголовок коммита пишется
на русском языке и может быть:

1. Предложением без подлежащего со сказуемыми в прошедшем времени.
2. Односоставным предложением без сказуемого.

Например,

```
Реализовал лесический анализ токенов Semicolon и Colon
```

или

```
Автоматический запуск тестов после сборки проекта
```

Не желательно, чтобы заголовок коммита был длиннее 60 символов. Не допустимо,
чтобы заголовок коммита был длиннее 70 символов.

Не допускается содержание категоризующих префиксов в заголовке коммита:
`fix(lexer)`, `[spec]`, `2A`, `ast:` и т.п.

Каждое предложение в описании коммита должно заканчиваться точкой. Не
допустимо, чтобы одна строка описания коммита была длиннее 70 символов.

## Разбиение изменений на коммиты

Изменения коммита должны соответствовать сообщению коммита. Например, если
изменения включают в себя новый функционал и исправление бага, то такие
изменения должны быть представлены в виде двух коммитов.

Не желательно вносить такие изменения в коммит, которые препятствуют сборке
проекта и мешают прохождению тестов (как юнит, так и приёмочных).

## merge-коммиты

Для merge-коммитов используются сообщения, автоматически сгенерированные git.

```
Merge branch 'feature/branching' into trunk
```

Запрещены merge-коммиты, появляющиеся при `git pull` (используйте `git pull --rebase`).

```
Merge remote-tracking branch 'origin/trunk' into trunk
```

## Антипаттерны

Запрещены коммиты по сообщению и содержанию вида:

1. "Навайбкодил кодогенерацию вызова функции"
2. "Хоп-хоп и в продакшн"
3. "Финальные правки перед сдачей"
4. "Кажется, теперь не падает", "Попробовал исправить баг?"
5. C чересчур общими сообщениями: `Исправления`, `Обновления`
6. Коммиты с артефактами сборки
